## Limits of this measurement

- Op latency runs from writing the op into the app to the receiver's inbound event
  (the gossip payload carrying that op). The op crosses several unordered `Update` hops
  — the input message → `write_ops` → `poll_p2p_events` on the sender, then
  `poll_p2p_events` → `drive` on the receiver — and each hop can cost a frame, so at
  60 Hz the ~50 ms p50 is a scheduling floor, not a transport number.
- `Achieved ops/s per peer` below 60 means the process could not hold the cadence; the
  latency in that row then measures queueing on top of that frame floor.
- The sender's own local apply and the rasterize/merge CPU cost are not part of it.
- Byte counts are gossipsub payloads (ops, anti-entropy announcements and repair
  frames). Transport framing, gossipsub metadata and identify/kad/ping are excluded.
- The anti-entropy announcement is 12 bytes per touched tile, so it grows with the
  painted area rather than with the canvas (1024 tiles fully painted would be ~12 KiB).
- Dropped means "never arrived as a gossip op": repair delivers a slice instead, so
  a dropped op still converges.
- The tap drains every ~1 ms; the `NetEventChannel` holds 1024 events, so a lagging
  tap would inflate the dropped rate.
- The 4 MiB GPU texture re-upload while painting (B4's open issue) needs a render
  world; headless only the CPU repaint above is measurable.
